Status: DRAFT — implementation blueprint generated from approved website-only docs.

## Purpose

This document defines implementation-ready rules for inquiry/contact form handling, Supabase lead storage and Resend email notifications.

Use this before backend/API/form tasks.

## Approved form stack

- Frontend/forms: Astro pages/components.
- Server endpoint: Vercel/Astro server route or equivalent server-only runtime.
- Anti-spam: Cloudflare Turnstile or equivalent plus honeypot.
- Lead storage: Supabase `inquiries` table only.
- Email notification: Resend.
- Analytics: Plausible-style privacy-friendly event tracking where appropriate.

## Scope rules

- Store only inquiry/contact leads in Supabase.
- Do not use Supabase as public content source of truth.
- Do not store inquiries in Sanity.
- Do not implement CRM integration in MVP.
- Do not collect unnecessary sensitive data.
- Do not log full message bodies or provider secrets.

## API endpoint: `POST /api/inquiries`

### Required request behavior

1. Accept only POST.
2. Parse body with size limit.
3. Normalize and validate fields.
4. Reject honeypot submissions without revealing anti-spam logic.
5. Verify Turnstile/equivalent server-side in production.
6. Apply rate limit before expensive provider calls where feasible.
7. Insert minimal lead record into Supabase with `retention_delete_after`.
8. Send Resend notification after successful insert.
9. Return safe JSON success/error response.

### Success response

Return generic success and user-facing expectation setting. Do not echo back full submitted message.

### Failure response rules

| Failure | User response | Internal handling |
|---|---|---|
| Validation fail | Field-level safe error | No provider call. |
| Honeypot fail | Generic rejection or silent success based on implementation | Mark as rejected if stored; otherwise no store. |
| Turnstile fail | “We could not verify the form. Please try again.” | No Supabase insert. |
| Rate limit | “Please wait before trying again.” | No Resend call. |
| Supabase insert fail | Generic server error | Safe log without message body; no false success. |
| Resend fail after insert | Success or partial operational notice based on UX decision | Preserve lead; log safe operational error for follow-up. |

## Resend notification template

### Required content

- New inquiry subject with source page/service context.
- Submitted name and contact method.
- Phone/email if provided.
- Service interest and location.
- Message body sanitized for email display.
- Source page and UTM summary.
- Internal note: do not reply if sender email is unverified unless template supports safe reply-to.

### Security rules

- `RESEND_API_KEY` is server-only.
- Recipient email(s) must come from approved environment variable or server config.
- Do not expose recipient list to client.
- Use safe HTML escaping or plain text for user content.

## Turnstile/equivalent rules

- Public site key may be client-side.
- Secret key must be server-side only.
- Verification response must be checked server-side.
- Local development may use provider test keys or a documented dev bypass that cannot be enabled in production.

## Rate limiting

Recommended MVP approach: per-IP and/or per-session rate limit on `/api/inquiries`, plus honeypot and Turnstile. If Vercel/serverless limitations prevent durable local rate limiting, document chosen provider/approach and mark verification status accordingly.

## Privacy notes

- Inquiry text may contain personal/confidential service details.
- Application logs must avoid full message content.
- Retention metadata must be present at insert time.
- Privacy microcopy must tell users data is used for responding to inquiry and retained according to policy.
- No marketing consent is implied by inquiry submission.

## Verification requirements

| Check | Evidence required | PASS rule |
|---|---|---|
| Valid submission | Request/response evidence and Supabase row screenshot/redacted output | Lead stored and success returned. |
| Resend delivery | Resend test/log screenshot with sensitive data redacted | Notification delivered or accepted by Resend. |
| Validation failure | Screenshot or test output | Invalid fields blocked. |
| Honeypot | Test output | Honeypot submission rejected or ignored. |
| Turnstile | Test output/log | Server verifies token; bad token fails. |
| Rate limit | Test output | Repeated submissions blocked or documented. |
| Secrets | Bundle/env inspection evidence | No server secrets exposed client-side. |
| Retention | Supabase row/migration evidence | `retention_delete_after` set to 6 months. |

## Launch blockers

- Form accepts unvalidated writes.
- Supabase service credentials exposed client-side.
- Resend API key exposed client-side.
- Turnstile secret exposed client-side.
- Leads can be publicly queried.
- Successful form path lacks Supabase storage or Resend notification evidence.
- Retention metadata missing.
